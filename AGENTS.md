## What this project is

**EcoConnect** is a hackathon web app (AWS Environmental Hacks, Oct 8–11, 2026). A user
describes unwanted items in plain language. **Amazon Bedrock** interprets the request
into a fixed taxonomy. **Deterministic rules** pick the routes (repair → reuse → donate →
e-waste → recycle). **DynamoDB** supplies human-verified local services in Faridabad.

## Golden rules (non-negotiable)

1. **Never invent data.** Do not write real-looking business names, addresses, phone
   numbers, coordinates, prices, opening hours or environmental impact numbers. Placeholder
   records must be obviously fictional ("Example Repair Shop", `+910000000000`) and have
   `isSample: true`. Humans write all provider data.
2. **The LLM interprets. It never decides facts.** Bedrock output is used only to produce an
   `Interpretation` (item types, conditions, quantities, location hint). Providers come
   only from DynamoDB. Trust comes only from `verification` metadata.
3. **Validate every boundary with zod:** API input, Bedrock output, seed data.
4. **Stay in scope.** Build only P0 and P1 items from `docs/PROJECT_SPEC.md` Part 3. No auth,
   marketplace, chat, admin panel, complaints system or extra AWS services unless an ADR
   in `docs/DECISIONS.md` approves it. Put ideas under "Later" in `docs/TASKS.md`.
5. **Shared code lives in `/shared` only.** `backend/src/shared/` and `web/src/shared/` are
   generated by `node scripts/sync-shared.mjs`. Never edit them directly.
6. **No secrets in git.** Use env vars. `.env*` files stay git-ignored. No AWS credentials in `web/`.
7. **Prove it works before saying "done".** Run the done-gate commands for the phase
   and report their actual output.

## Stack (do not change without an ADR)

- `web/`: Next.js App Router, TypeScript strict, Tailwind CSS, `output: 'export'`, `lucide-react`
- `backend/`: AWS SAM, API Gateway HTTP API, Lambda (Node.js + TypeScript, esbuild),
  DynamoDB, Bedrock Converse API (`@aws-sdk/client-bedrock-runtime`), zod, vitest
- Hosting: AWS Amplify Hosting (static). Logs: CloudWatch

## Commands

| Task | Command |
|---|---|
| Sync shared code | `node scripts/sync-shared.mjs` |
| Backend tests | `cd backend && npm test` |
| Backend typecheck | `cd backend && npx tsc --noEmit` |
| Golden AI eval (calls Bedrock) | `cd backend && npm run eval:golden` |
| Deploy backend | `cd backend && sam build && sam deploy` |
| Seed data | `cd backend && npm run seed -- --file ../data/providers/faridabad.json --table <TableName>` |
| Validate data only (no AWS) | `cd backend && npm run seed -- --file ../data/providers/faridabad.json --dry-run` |
| Smoke test API | `cd backend && API_URL=<url> ./scripts/smoke.sh` |
| Web dev | `cd web && npm run dev` |
| Web checks | `cd web && npm run lint && npx tsc --noEmit && npm run build` |

Update this table when a command changes.

## Coding conventions

- TypeScript `strict: true`. No `any` unless you comment why.
- Pure logic (rules, matching, classification, geo) lives in `backend/src/lib`, has no
  AWS imports, and has unit tests.
- Handlers stay thin: validate → call lib → shape response → log one JSON line.
- Use the error shape `{ error: { code, message } }` and the status codes from spec 2.7.
- Render all AI free-text as plain text. Never use `dangerouslySetInnerHTML`.
- UI is mobile-first (375 px), accessible (labels, focus states, AA contrast), and every
  state is designed (loading, empty, error, fallback mode).
- Prefer small files and clear names over clever abstractions. Don't add dependencies
  without a reason in your plan.

## Workflow for every task

1. Say which phase or `TASKS.md` item you're working on.
2. Propose a short plan (files plus responsibilities). Wait for approval if the human asked for that.
3. Implement in small steps. Run tests and typecheck as you go.
4. Run the phase done-gate. Paste the results.
5. Suggest a conventional commit message (`feat:`, `fix:`, `chore:`, `docs:`, `test:`).
6. Tick the item in `docs/TASKS.md`. Add an ADR to `docs/DECISIONS.md` if a decision changed.

## When unsure

Ask the human. Don't guess requirements, don't guess AWS console state, and never guess data.
